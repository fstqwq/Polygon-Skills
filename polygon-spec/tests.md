# tests/spec.json  --  Full Schema

```json
{
  "tests": [
    {
      "id": "001",
      "kind": "manual",
      "sample": true
    }
  ]
}
```

| Field | Type | Note |
|-------|------|------|
| `id` | string | unique 3-12 digit decimal token |
| `kind` | string | `"manual"` or `"gen"` |
| `sample` | bool | optional JSON boolean; absence means `false`; write only `true` |
| `sample_input` | string | optional statement-only override for one displayed input/output pair. Leave absent for ordinary samples. |
| `sample_output` | string | optional statement-only override for one displayed input/output pair. Leave absent for ordinary samples. |
| `sample_output_validate` | bool | optional; default `true`. Relevant only when `sample_output` is present. If `false`, the sample output is displayed in the statement but **not checked** during verification. Only written when `false`. |
| `sample_json` | object | optional complete structured statement presentation. Use `pair` for explicit input/output pairs and `interaction` for an ordered interactor/solution transcript. |

## Structured sample presentation

`sample_json` changes only what the statement displays. The testcase still uses
`tests/manual/{id}.in` or `tests/generator/{id}.in` for judging. A structured
sample is a complete authored presentation and does not need Verification
artifacts to fill any of its passes.

Use `presentation: "pair"` for a single-pass or multi-pass list of input/output
pairs:

```json
{
  "id": "001",
  "kind": "manual",
  "sample": true,
  "sample_json": {
    "presentation": "pair",
    "passes": [
      {"number": 1, "input": "3 1\n", "output": "4\n"},
      {"number": 2, "input": "3 2\n", "output": "5\n"}
    ]
  }
}
```

Use `presentation: "interaction"` for an interactive transcript. Events remain
in display order; `interactor` is data sent to the solution and `solution` is
data sent by the solution:

```json
{
  "id": "002",
  "kind": "manual",
  "sample": true,
  "sample_json": {
    "presentation": "interaction",
    "passes": [
      {
        "number": 1,
        "events": [
          {"source": "interactor", "content": "3\n"},
          {"source": "solution", "content": "2\n"},
          {"source": "interactor", "content": "correct\n"}
        ]
      }
    ]
  }
}
```

The structured contract is strict:

- `sample` must be `true`.
- `sample_json` contains only `presentation` and `passes`; `passes` is non-empty.
- Passes are numbered from 1 in array order without gaps. `number` may be
  omitted, in which case its 1-based array position is used.
- A `pair` pass contains only `number`, `input`, and `output`; both text fields
  are required strings.
- An `interaction` pass contains only `number` and `events`. Each event contains
  only `source` and `content`; `source` is `interactor` or `solution`, and
  `content` is a string. Empty event arrays and empty content are valid.
- Do not combine `sample_json` with `sample_input` or `sample_output`. Omit
  `sample_output_validate` for structured samples.
- Unknown fields are invalid at every level.

File conventions:
- `tests/spec.json` itself is required, even when its canonical content is
  `{ "tests": [] }`.
- Its top level must be an object containing only `tests`. A top-level array,
  unknown keys, string booleans, missing `id` or `kind`, and duplicate IDs are
  invalid.
- Each `kind: "manual"` test must have `tests/manual/{id}.in` containing the test input.
- Each `kind: "gen"` test must have `tests/generator/{id}.in` containing the generator command (e.g., `gen_random 5 100 1`).
- The first generator command token must resolve unambiguously to a source
  selected by `config/build.json.generator_sources`. A generator file that is
  not selected is unavailable to tests. The command may use the repo-relative
  path, the path below `generators/`, or an unambiguous basename, with or
  without its extension.
- Do not write `tests/answers/{id}.ans`. The source repository and exported package must not contain committed answer files.
- Official answers are generated by the verification/package pipeline from the accepted solution. Use `sample_input`/`sample_output` for an intentional single-pair display override; use `sample_json` when the statement needs multiple passes or an ordered interaction transcript.
- Input files must end with exactly one newline and have no trailing spaces per line.
- Ordinary sample tests should rely on `tests/manual/{id}.in`; displayed output comes from generated official answers. Do not add any display override unless the statement intentionally differs from that evidence.

Test count and coverage:
- Most finished problems should have roughly 20-70 tests. Fewer than 20 tests needs an explicit reason.
- Random/stress tests must repeat each important parameter shape with several different seeds. Default to at least 3 seeds per shape.
- Boundary-sensitive shapes must include off-by-one variants such as `n = N - 1` and `n = N`, `m = M - 1` and `m = M`, and `value = max - 1` and `value = max` when meaningful.
- A single random test does not cover a category. Treat a random category as covered only after repeated seeds and after checking that output branches are represented.
- Integer-heavy problems must include overflow-oriented cases: values near common type limits, sums/products/squared values beyond 32-bit, and mixed small/large values when allowed.
- Floating-point problems must include precision-oriented cases: near-zero answers, tolerance-boundary answers, mixed magnitudes, and near-degenerate geometry or algebraic configurations when applicable.

# solutions/*.desc

```
expected: accepted
```

Valid `expected` values:

| Value | Meaning |
|-------|---------|
| `accepted` | Must pass all tests |
| `wrong_answer` | Expected to fail with WA on at least one test |
| `tle_or_correct` | Algorithmically correct, but may either pass or hit TL under the configured limits |
| `tle_or_re` | Expected to hit TL or RE, either outcome is acceptable |
| `time_limit_exceeded` | Expected to hit TL on at least one test |
| `run_time_error` | Expected to hit RE on at least one test |
| `rejected` | Generic negative solution; expected to fail by WA, TL, or RE |
| `unknown` | No required verdict; used for an explicitly unclassified solution |

A descriptor is optional. A source without one has `unknown` expected behavior.
When present, a descriptor contains exactly one `expected:` line followed by
zero or more non-empty `note:` lines. `behavior:`, `verdict:`, unkeyed lines,
duplicate `expected:` fields, and filename-based behavior inference are invalid
authored syntax. `config/build.json.accepted_solution_source` is authoritative:
that selected solution is accepted even when its descriptor is absent or says
something else.

# draft/ Conventions

The `draft/` directory holds working documents used during problem authoring. It is **git-tracked** and **excluded from zip packages**.

## draft/statement.md

Write the problem statement in Markdown before converting to LaTeX.

**Do:**
- Use `$...$` for inline math and `$$...$$` for display math
- Use plain prose for constraint descriptions; list ranges in a table if helpful
- Use fenced code blocks for sample input/output
- Mark which samples should appear in the statement

**Don't:**
- Do not write LaTeX commands (`\texttt`, `\le`, `\begin{itemize}`, etc.)
- Do not invent constraints or examples the user hasn't confirmed
- Do not mix test data with the statement draft

## draft/solution.md

Write the algorithm sketch and solution analysis.

**Do:**
- State key observations clearly
- Write complexity analysis: `O(n log n) time, O(n) space`
- Note expected behavior of WA/TLE solutions (e.g., "greedy fails on star graphs")
- Reference which algorithm each solution file implements

**Don't:**
- Do not write complete compilable code (that goes in `solutions/`)
- Do not describe input format here (that belongs in the statement)

## draft/notes.md

Free-form working notes: open questions, references, discussion history, todo items. No structure required.
